## 0. Resumen ejecutivo y hallazgos de auditoría

Cowinance ya tiene una dirección visual madura y correcta (verde bosque + neutros cálidos + Inter + `tabular-nums`, cercana a Linear/Stripe). P1.4.1 cimentó la **fuente única de tokens** para color/radio/sombra/fuente. Lo que falta —y lo que esta spec define— es **todo lo que hoy vive como números mágicos dispersos**: escala tipográfica, escala de spacing, densidad, contrato de iconografía, motion, accesibilidad y responsive.

**Hallazgos cuantitativos (auditados en el código, no estimados):**

| Área | Estado real hoy | Implicación |
|---|---|---|
| **Tipografía** | **18 tamaños distintos** `text-[Npx]` en web (9,10,11,12,13,14,15,16,17,20,22,24,26,28,30,56,64). Workhorse: 13px (**103 usos**), 12px (83), 11px (33). Sin nombres. | Hay una escala *de facto* escondida en magic numbers. Hay que nombrarla, no inventarla. |
| **Pesos** | 4 en uso: `font-medium` (97), `font-semibold` (53), `font-bold` (14), `font-normal` (6). | Consolidar en 400/500/600/700; acotar 700 a display. |
| **Line-height** | Casi ausente (`leading-9` ×2, `leading-none` ×3, `leading-5` ×1). Resto default del navegador. | Ritmo vertical no controlado → definir line-height por rol. |
| **Divergencia web/móvil** | KPI web **30px** vs móvil **26px**; padding de Card web **20px** (`p-5`) vs móvil **16px**; web **no tiene** primitivo `Button`, móvil **sí**. | Mismos roles con valores distintos por accidente, no por decisión. |
| **Spacing** | Escala Tailwind (4px) con **muchos medios pasos** (`mt-0.5`=2, `gap-1.5`=6, `px-2.5`=10, `py-0.5`=2). Comunes: `px-3`(12), `gap-2/3`(8/12), `p-5/6`(20/24). | Grid base 4px con sub-unidad de 2px, ya *de facto*. |
| **Color** | **Bien tokenizado** (primitivos + semánticos claro/oscuro). Convención `status/10` fondo + `status/30` borde en badges. | Solo falta formalizar reglas de uso y jerarquía. |
| **Dark mode** | **Existe por accidente**: web sigue `@media (prefers-color-scheme: dark)` (heredado); móvil **solo claro** (`const L = semantic.light`). Contrastes dark **sin auditar**. | Estado inconsistente y no decidido. Ver §6. |
| **Iconos** | Dos librerías: `lucide-react` (web, 20 imports, `size` 14–18, `strokeWidth 1.75`) + `@expo/vector-icons`/Ionicons (móvil, `size` 15–30). | Coexisten; falta contrato de significado/tamaño/estado. Ver §7. |
| **Responsive** | Mínimo: `lg:` (12), `md:` (9), `sm:` (1). Sidebar `max-lg:hidden`. | **Gap real:** por debajo de `lg` la web se queda **sin navegación**. Ver §11. |
| **Densidad** | No existe. | Contrato nuevo. El ERP la necesita. Ver §4. |

**Principio rector (heredado de la auditoría P1.4, confirmado):** *no se reinventa el look de Cowinance — se sistematiza y fortalece.* Todo lo de esta spec es **behavior-preserving en intención**: nombrar y ordenar lo que ya existe, resolver divergencias accidentales, y dejar contratos para lo que aún no existe.

**Decisiones que afectan la arquitectura (consolidadas en §14):**
1. Dónde vive la escala tipográfica y **si genera utilidades Tailwind** (`@theme`) o clases semánticas.
2. **Densidad como capa multiplicadora** en runtime (`data-density` + CSS vars), nunca horneada en componentes.
3. **Dark mode web = controlado por usuario** (`data-theme`), migrando desde el `@media` accidental; **móvil = claro primero, dark diferido**.
4. **Navegación web por debajo de `lg`** (hoy inexistente).
5. Contrato de iconos = **mapa semántico** compartido, dos librerías permitidas (no elegir vendor único aún).

## 1. Filosofía del Design System

### 1.1 Principios de diseño

1. **Densidad honesta.** Cowinance es un ERP agropecuario: el usuario administra cientos/miles de animales, lotes, tratamientos y pesajes. La UI prioriza **información por pantalla** sobre aire decorativo. El body de 13px y `tabular-nums` no son un accidente: son la decisión correcta (Linear/Stripe/Notion-database). El sistema **no** debe "esponjar" la información.
2. **Una regla visual, un solo lugar.** Extensión directa de la regla de arquitectura del proyecto (una regla de negocio = un lugar). Ningún valor visual (tamaño, color, espacio, duración) se escribe a mano dos veces. La fuente es `packages/design-tokens/src/tokens.ts`; los artefactos se **derivan** (ADR-0013).
3. **El campo manda en móvil; la oficina manda en web.** Divergencia deliberada ya consagrada en ADR-0012. El móvil es compañero de campo (offline, luz solar, guantes, una mano); la web es escritorio de administración (sesiones largas, teclado, densidad). El sistema visual sirve a **dos contextos**, no a uno.
4. **Accesible por defecto, no como parche.** AA es el piso, no la meta (§10). Estado nunca solo por color; foco siempre visible; touch targets reales.
5. **Comportamiento antes que patrón (YAGNI visual).** No se crea un primitivo, un token ni una variante sin un consumidor real. Igual criterio que los VO/DomainError del dominio (ADR-0006). "Tabla universal sin consumidores" está prohibido.
6. **Sistematizar, no rediseñar.** El look actual es correcto. El trabajo es ordenarlo y escalarlo, preservando la identidad.

### 1.2 Objetivos

- **O1.** Eliminar los números mágicos tipográficos (18 tamaños → una escala nombrada).
- **O2.** Dar ritmo vertical y espacial predecible (grid base + escala de spacing).
- **O3.** Habilitar **densidad configurable** (cómodo/estándar/compacto) sin re-arquitectura.
- **O4.** Resolver la incógnita **dark mode** con una decisión razonada, no un accidente.
- **O5.** Un **contrato de iconografía** que unifique significado entre dos librerías.
- **O6.** Un **inventario de componentes** clasificado, con prioridad y consumidores.
- **O7.** Estándares transversales: motion, accesibilidad, responsive.
- **O8.** Cerrar la divergencia web/móvil **accidental** (KPI 30/26, padding 20/16, Button) manteniendo la **deliberada** (contextos).

### 1.3 Restricciones (técnicas y de producto)

- **R1 — Pipeline de tokens ADR-0013.** La fuente es TS neutral; web consume **CSS en build-time** (Tailwind v4 es CSS-first, `@theme`), móvil consume **objeto JS** (RN quiere números, no strings `px`). Toda extensión (tipografía, spacing, densidad) debe pasar por este doble target o no entra.
- **R2 — Behavior-preserving.** La API, la convergencia de sync y la UI existente deben seguir idénticas hasta que la aplicación de la escala (P1.4.3+) se apruebe. Playwright 5/5 es gate.
- **R3 — Sin dependencias nuevas si un script propio alcanza.** Igual criterio que "no Style Dictionary por ahora" (ADR-0013 D). Un generador ampliado supera a una lib pesada para ~2 targets.
- **R4 — Móvil offline-first real.** Cualquier decisión visual (p.ej. dark en runtime) no puede depender de red ni romper el store local.
- **R5 — Dos plataformas, dos runtimes.** Next 15 (RSC, sin flicker de tema antes del paint) y Expo 57/Metro (linkeo de packages del workspace quisquilloso). Ver §12.
- **R6 — Sin CI todavía.** Los gates se corren a mano; agregar dark/densidad multiplica combinaciones de QA visual (§12).

### 1.4 Relación con la arquitectura existente y los ADR

- **ADR-0013 (tokens):** esta spec es su continuación natural declarada ("Fuera de alcance P1.4.2+: escala tipográfica, spacing, densidad, dark, iconografía, primitivos"). Todo lo de acá **extiende** ese pipeline, sin re-arquitectura.
- **ADR-0012 (onboarding):** consagra la divergencia web/móvil por contexto. Esta spec la respeta y solo cierra las divergencias **accidentales**.
- **ADR-0004/0006 (dominio puro, YAGNI):** el mismo rigor se aplica al frontend: ningún primitivo/token especulativo.
- **Backend:** el Design System **no toca** el backend. Los valores derivados de reglas (retiro, gestación, categoría) siguen siendo autoridad del servidor (ADR-0007); la UI solo los presenta. La spec presenta datos con `tabular-nums` y estados con color+icono+texto, pero **no** recalcula ni decide reglas. El contrato es unidireccional: dominio → UI.

## 2. Escala tipográfica

**Fuente única:** Inter (`--font-inter`), fallback `ui-sans-serif, system-ui`. Mono: `ui-monospace, 'JetBrains Mono', 'SF Mono', Menlo` (ya en tokens). `font-feature-settings: 'ss01'` en body (ya activo). `tabular-nums` para todo dato numérico.

**Diseño de la escala.** Es **role-based**, no size-based: se nombra por función (lo que evita que un dev elija "22px porque sí"). Es **densa en el rango chico** (11–15) —correcto para ERP— y más holgada arriba. Cubre los 18 tamaños actuales colapsándolos a **11 roles**.

| Rol (nombre oficial) | Size | Line-height | Peso default | Tracking | Uso recomendado | Reemplaza hoy |
|---|---|---|---|---|---|---|
| `type-display` | 30 / 1.2 (36px) | 600 | −0.02em | Números KPI grandes, stat hero | `text-[30px]`, unifica móvil 26 |
| `type-title` | 20 / 1.4 (28px) | 600 | −0.01em | Título de página (h1) | `text-[20px]`, `text-[22px]` |
| `type-heading` | 17 / 1.4 (24px) | 600 | −0.01em | Encabezado de sección (h2) | `text-[17px]` |
| `type-subheading` | 15 / 1.45 (22px) | 600 | 0 | Título de card (h3) | `text-[15px]` (11 usos) |
| `type-body` | **13 / 1.55 (20px)** | 400 | 0 | **Cuerpo y celdas de tabla (workhorse)** | `text-[13px]` (**103**) |
| `type-body-strong` | 13 / 1.55 (20px) | 500 | 0 | Cuerpo enfatizado, valor de fila | subset de 13px medium |
| `type-label` | 12 / 1.35 (16px) | 500 | 0 | Etiquetas de formulario, hints | `text-[12px]` (83) |
| `type-caption` | 11 / 1.45 (16px) | 500 | +0.01em | Metadatos, timestamps, badges | `text-[11px]` (33), `text-[10px]` |
| `type-overline` | 11 / 1.35 (16px) | 600 | +0.06em · UPPERCASE | Divisores de sección (nav, grupos) | `tracking-[0.06em] uppercase` |
| `type-input` | **14 / 1.4 (20px)** | 400 | 0 | Texto dentro de inputs/controles | `text-[14px]` (16) — ver nota |
| `type-mono` | 13 / 1.55 (20px) | 500 | +0.01em · tabular | Caravanas, IDs, números críticos | `font-mono text-[13px]` |

**Tier expresivo (fuera de banda, uso acotado):** `type-hero` 40–56 y `type-hero-lg` 56–64, **solo** en pantallas de auth/marketing (login, hero de bienvenida). No entra al lenguaje de datos del ERP. Reemplaza los `text-[56px]`/`text-[64px]` (2 usos c/u).

**Notas y reglas de la escala:**
- **Body 13 vs Input 14 es deliberado.** El input sube a 14px por comodidad de tipeo y target táctil; iOS además evita el auto-zoom con ≥16px, a evaluar para campos móviles críticos (nota para §12). El cuerpo de lectura densa se queda en 13.
- **Un solo workhorse.** 13px es el 60%+ del texto. La escala se construye alrededor de él.
- **Pesos:** 400 (cuerpo), 500 (labels/énfasis), 600 (encabezados/KPI), 700 **reservado a display/hero**. Se retira el `font-bold` ad-hoc del cuerpo (14 usos a auditar en P1.4.3).
- **Jerarquía completa (de mayor a menor):** hero → display → title → heading → subheading → body-strong → body → label → caption/overline. Overline y caption comparten tamaño (11) pero difieren en peso/tracking/caso: overline estructura, caption informa.
- **La escala NO define color.** Un `type-body` puede pintarse `text-primary`, `text-secondary` o `text-tertiary` según jerarquía de color (§5). Tamaño y color son ejes ortogonales.

**⚠️ DECISIÓN A — dónde vive la escala y cómo se consume (ver §14).** Dos opciones (recomendación en §14).

## 3. Sistema de spacing

### 3.1 Grid base

- **Unidad base: 4px.** Es la unidad de Tailwind y la dominante en el código.
- **Sub-unidad: 2px** (medio paso) para ajustes ópticos e insets finos (badges, chips, separación icono-texto). Ya se usa de facto (`mt-0.5`, `py-0.5`, `px-2.5`). Se admite **explícitamente** pero acotada: 2px no es de layout, es de detalle.

**⚠️ DECISIÓN B (parte 1):** admitir el grid **4px con sub-unidad 2px documentada** (recomendado) vs forzar 4px puro (rompería/rediseñaría los medios pasos actuales). Ver §14.

### 3.2 Escala de spacing (múltiplos)

| Token | px | Múltiplo | Uso típico |
|---|---|---|---|
| `space-0` | 0 | — | reset |
| `space-px` | 1 | — | hairline/border |
| `space-0.5` | 2 | 0.5× | inset óptico, badge padding-y |
| `space-1` | 4 | 1× | gap mínimo icono-texto |
| `space-1.5` | 6 | 1.5× | gap compacto |
| `space-2` | 8 | 2× | gap de controles, padding chico |
| `space-3` | 12 | 3× | **padding horizontal estándar** (`px-3`) |
| `space-4` | 16 | 4× | padding de card (móvil), gap de grupo |
| `space-5` | 20 | 5× | padding de card (web), separación media |
| `space-6` | 24 | 6× | padding de página, separación de bloque |
| `space-8` | 32 | 8× | separación entre secciones |
| `space-10` | 40 | 10× | separación amplia, empty states |
| `space-12` | 48 | 12× | márgenes de layout |
| `space-16` | 64 | 16× | separaciones hero |

La escala es **densa abajo, holgada arriba** (paralela a la tipografía). Cubre el 100% de los valores observados.

### 3.3 Ritmo vertical

- **Unidad de ritmo: 4px**, anclada al line-height del body (`type-body` = 20px = 5×4). Todo alto de línea es múltiplo de 4 → los textos caen en la grilla.
- **Baseline de datos:** en tablas y listas, la altura de fila es múltiplo de 4 y contiene un `type-body` centrado verticalmente; los números `tabular-nums` no descuadran columnas.

### 3.4 Separación entre componentes y entre secciones

| Relación | Recomendado | Nota |
|---|---|---|
| Dentro de una card (label→valor) | 4–8 (`space-1`/`space-2`) | denso |
| Entre campos de un formulario | 12–16 (`space-3`/`space-4`) | según densidad (§4) |
| Entre cards de una grilla | 12–16 (`gap-3`/`gap-4`) | KPI grid |
| Entre bloques dentro de una sección | 16–24 (`space-4`/`space-6`) | |
| **Entre secciones de página** | 24–32 (`space-6`/`space-8`) | |
| Padding de página (contenido) | 24 (`space-6`) | escala con densidad |

### 3.5 Densidad ERP — cómo el spacing soporta cada superficie

El sistema de spacing debe sobrevivir a **cinco superficies** con exigencias opuestas:

1. **Escritorio (web):** el más denso. Sidebar 240px fija; contenido con padding 24; grillas de 2–4 columnas. El spacing chico (2–12) domina.
2. **Móvil (app):** una mano, pulgar, luz solar. Targets ≥44px, padding lateral 16, separación entre tarjetas 12. La escala **no cambia**, cambian los mínimos táctiles (§10) y el default de densidad (móvil = estándar/cómodo, nunca compacto por debajo del piso táctil).
3. **Tablas densas:** el caso más exigente. Fila de 32–48px según densidad; padding de celda horizontal 12, vertical mínimo; `tabular-nums` obligatorio; separadores `border-subtle` en vez de espacio. El spacing vertical de fila es el **eje principal de la densidad** (§4).
4. **Formularios grandes (manga/captura, alta de animal):** campos en columna, gap 12–16, agrupación por `type-overline` + `space-6` entre grupos. En captura de manga (una acción tras otra, cientos de veces) prima la densidad compacta y el foco automático; el spacing no puede meter scroll de más.
5. **Dashboards:** grilla de KPIs (`gap-3`/`gap-4`), cards con padding 20 (web). Mezcla de densidad de dato (KPI grande) y densidad de lista (alertas, próximos vencimientos).

**Contrato:** la escala de spacing es **única y fija**; lo que varía por superficie/densidad son **qué peldaños de la escala** se eligen para paddings verticales y alturas de fila/control (§4), nunca los valores de la escala en sí.

## 4. Sistema de densidad

**No se implementa aquí. Se define el contrato.** Es la pieza más sensible arquitectónicamente: si los componentes hornean alturas/paddings fijos (como hoy), la densidad se vuelve **imposible de agregar después**. Por eso el contrato debe existir **antes** de P1.4.3.

### 4.1 Los tres modos

| Modo | Contexto primario | Filosofía |
|---|---|---|
| **Cómodo** | Móvil, usuarios nuevos, pantallas táctiles | Máxima legibilidad y target; menos filas por pantalla |
| **Estándar** | Default web y móvil | Equilibrio |
| **Compacto** | Power-users web, tablas grandes, manga | Máxima densidad de datos; solo pointer o con piso táctil respetado |

### 4.2 Qué cambia (y solo esto)

La densidad es una **capa multiplicadora** sobre **spacing y alturas**, expresada como CSS custom properties resueltas en runtime:

| Variable de densidad | Cómodo | Estándar | Compacto | Qué controla |
|---|---|---|---|---|
| `--control-h` | 44 | 36 | 32* | Alto de input/botón/nav-item |
| `--row-h` | 48 | 40 | 32* | Alto de fila de tabla/lista |
| `--pad-y` | 12 | 8 | 6 | Padding vertical de contenedores |
| `--gap` | 16 | 12 | 8 | Separación entre elementos de grupo |
| `--card-pad` | 24 | 20 | 16 | Padding de card |

\* En **compacto**, 32px solo es válido en dispositivos **pointer** (mouse). En touch, el piso es **44px** (§10) — el modo compacto **no puede** violar el target táctil; en touch, "compacto" colapsa a los valores de estándar para alturas interactivas.

### 4.3 Qué NUNCA cambia con la densidad

- **La escala tipográfica** (tamaños, pesos, line-height). Un compacto no achica la letra; achica el aire. (Excepción única a evaluar: `type-display` de KPI puede tener un peldaño por densidad, decisión de P1.4.4.)
- **Los tokens de color** ni su significado.
- **El radius**, las sombras, la iconografía (tamaños de icono son función del texto, no de la densidad).
- **La arquitectura de información:** qué se muestra y en qué orden. Densidad ≠ ocultar datos.
- **Los mínimos de accesibilidad:** foco, contraste, target táctil (44px en touch, siempre).

### 4.4 Arquitectura del contrato

- Densidad se aplica vía atributo `data-density="comodo|estandar|compacto"` en un ancestro (root o contenedor), que **redefine las CSS vars** de §4.2. Los componentes leen `var(--control-h)`, nunca un `h-9` hardcodeado.
- **No puede ser `@media`**: es una preferencia de usuario en runtime, no del dispositivo. → requiere atributo + contexto (React), igual patrón que el dark mode controlado (§6).
- Móvil (RN, sin CSS vars): la densidad se resuelve como un **objeto de tema derivado** (`densityTheme[mode]`) que multiplica los mismos valores; el adaptador `theme.ts` ya es el lugar natural.
- **Regla para P1.4.3:** al aplicar la escala, **prohibido hornear alturas/paddings verticales fijos** en primitivos interactivos; deben referenciar la capa de densidad aunque en P1.4.3 esa capa tenga un solo valor (estándar). Así, agregar cómodo/compacto en P1.4.7 es cambiar tokens, no reescribir componentes.

**⚠️ DECISIÓN C:** introducir la **capa de densidad como tokens desde P1.4.3** (aunque con un solo modo activo), para no rehacer componentes luego. Recomendado. Ver §14.

## 5. Sistema de colores

**No se cambia la paleta.** Ya está tokenizada (primitivos brand/amber + semánticos claro/oscuro). Se **especifica su uso**.

### 5.1 Tokens semánticos (contrato de significado)

| Grupo | Tokens | Significado |
|---|---|---|
| Fondo | `bg-canvas`, `bg-surface`, `bg-sunken`, `bg-raised` | Lienzo de app / superficie de card / hundido (inputs, tracks) / elevado (menús, popovers) |
| Borde | `border-subtle`, `border-strong` | Separador suave (tablas, cards) / borde de control (inputs) |
| Texto | `text-primary`, `text-secondary`, `text-tertiary` | Jerarquía de lectura (§5.3) |
| Estado | `status-success`, `status-warning`, `status-danger`, `status-info` | Semántica, no decoración |
| Acento | `accent`, `accent-soft` | Marca/acción primaria (`brand-700` claro) / fondo de acento (`brand-100`) |
| Elevación | `shadow-1/2/3` | Profundidad creciente |

### 5.2 Reglas de uso

1. **Color = significado, no decoración.** El verde brand es **acción/marca**; el verde `status-success` es **estado positivo**. No intercambiables (hoy son hex distintos: `brand-700` `#1f4e3d` vs `success` `#1e7f4f`). Nunca usar un status para pintar algo que no es ese estado.
2. **Fondos de estado por convención.** Badges/alerts usan `status/10` (fondo) + `status/30` (borde) + `status` (texto/icono). Ya en uso (`StatusBadge`); se formaliza.
3. **Texto sobre color:** sobre `accent` (brand-700), texto blanco. Sobre `accent-soft` (brand-100), texto `text-primary` o `accent`. Verificar contraste (§5.4).
4. **Superficies apiladas:** canvas < sunken < surface < raised en jerarquía de elevación; no saltar niveles arbitrariamente.
5. **Neutro por defecto.** La mayoría de la UI es neutra (texto + bordes). El color se **reserva** para acción y estado. Una pantalla con demasiado color pierde la señal.

### 5.3 Jerarquía de color de texto

- `text-primary` (#191c1a): contenido principal, valores, encabezados.
- `text-secondary` (#5a605c): labels, texto de apoyo, valores secundarios.
- `text-tertiary` (#8b918d): metadatos, placeholders, hints de baja prioridad, iconos decorativos.
- **Regla:** la jerarquía se construye **primero con color de texto y peso**, y solo después con tamaño. Un `type-body` en `text-tertiary` ya comunica "secundario" sin achicar la letra.

### 5.4 Accesibilidad y contraste (ver §10 para el estándar completo)

- Piso **AA**: 4.5:1 texto normal, 3:1 texto grande (≥ `type-heading`) y componentes UI/bordes de foco.
- `text-tertiary` sobre `bg-canvas`: **verificar** que alcance 4.5:1 para texto de cuerpo; si solo llega a ~3:1, restringirlo a texto ≥ large o a rol no esencial (metadato). **Auditoría pendiente en P1.4.3** con herramienta de contraste sobre los pares reales.
- **Estado nunca solo por color:** todo estado lleva **color + icono + texto** (un daltónico no distingue success/danger). Ya se respeta en badges con label; se vuelve regla.

### 5.5 Cuándo usar color y cuándo no

- **Usar:** acción primaria (brand), estados (success/warning/danger/info), selección/activo (accent-soft), datos críticos que requieren atención inmediata (retiro vencido = danger).
- **No usar:** para jerarquía que el peso/tamaño ya resuelve; para decorar cards; para diferenciar categorías sin significado de estado (usar texto/icono); nunca como único portador de información.

## 6. Dark Mode — análisis y recomendación

**No se asume que habrá dark mode.** Se decide.

### 6.1 Estado real (hallazgo)

- **Web:** hay dark **por accidente heredado** — `@media (prefers-color-scheme: dark)` en el CSS generado. Sigue el SO automáticamente. Los tokens dark existen pero sus **contrastes no fueron auditados** (el handoff lo llama "dark preexistente, reproducido igual").
- **Móvil:** **solo claro** (`theme.ts` usa `semantic.light`). Sin dark.
- **Consecuencia:** hoy la experiencia es **inconsistente y no intencional** (web puede verse oscura sin que nadie lo decidiera; móvil nunca).

### 6.2 Análisis por dimensión

| Dimensión | Web (oficina) | Móvil (campo) |
|---|---|---|
| **Experiencia en oficina** | Dark valioso en sesiones largas, luz controlada, menos fatiga. **A favor.** | N/A |
| **Experiencia bajo el sol** | N/A | Dark **peor** bajo sol directo: fondos oscuros con texto claro pierden contraste percibido en exteriores; el claro (fondo claro, texto oscuro) se lee mejor con brillo alto. **En contra de dark en campo.** |
| **Accesibilidad** | Ambos modos deben cumplir AA por separado. Dark requiere re-auditar contrastes (hoy sin auditar). Costo real. | Claro cumple hoy; dark agregaría una segunda auditoría sin beneficio de campo. |
| **Costo de mantenimiento** | Cada componente × 2 temas (× 3 densidades futuras) = QA combinatorio. Playwright ya hace screenshots → se pueden agregar en dark, pero crece el gate. | Igual costo, menor retorno (RN además duplica lógica de tema). |
| **Consistencia web/móvil** | Web-dark + móvil-claro = divergencia. Pero **justificada por contexto** (misma lógica que ADR-0012: oficina ≠ campo). | |

### 6.3 Recomendación

1. **Web: soportar dark, pero migrarlo de accidente a decisión.** Cambiar de `@media (prefers-color-scheme)` **automático** a **controlado por usuario** (`data-theme="light|dark"`, default claro, con el SO como pista inicial). Razón: en trabajo de datos, el cambio automático a media mañana es disruptivo; el usuario de ERP quiere **control explícito**. Y hacer dark un **target de primera clase auditado** (contraste AA en dark + screenshots Playwright), no un estado no probado.
2. **Móvil: claro primero, dark diferido.** El contexto de campo hace del claro la prioridad; un dark a medias que falla bajo sol es peor que no tenerlo. Los tokens dark **ya existen** en la fuente (se conservan), pero **no se cablea** el dark móvil hasta que haya (a) demanda real y (b) prueba de campo. Documentar como deuda intencional.
3. **Secuenciación:** dark web se pule en **P1.4.7** (no antes), cuando escala/densidad/primitivos ya estén estables — así se audita dark una sola vez sobre un sistema cerrado, no sobre un blanco móvil.

**⚠️ DECISIÓN D:** migrar web a `data-theme` controlado + dark como target auditado en P1.4.7; móvil claro-primero con dark diferido. Esto cambia la **generación del CSS de tokens** (hoy `@media`; pasaría a `@media` como default + override por `[data-theme]`, y un script inline anti-FOUC en Next). Ver §12 y §14.

## 7. Contrato de iconografía

**No se elige librería única todavía.** Se define el **lenguaje** que ambas deben hablar.

### 7.1 Realidad (hallazgo)

- Web: `lucide-react` (outline, `strokeWidth 1.75`, `size` 14–18 en uso).
- Móvil: `@expo/vector-icons`/Ionicons (`size` 15–30, variantes `-outline` y filled).
- **Coexisten y está bien** (YAGNI: no hay razón para forzar una lib cross-platform hoy). El contrato es el **significado y la forma**, no el vendor.

### 7.2 Contrato

| Aspecto | Regla |
|---|---|
| **Tamaños** | Ladder anclado al texto: **14** (inline denso, con 12–13px), **16** (default, con body), **18** (nav/énfasis), **20** (botones/sección), **24** (empty states, tab bar móvil), **28–32** (hero/FAB). Nada fuera del ladder. |
| **Grosor** | Canónico **1.75px** de trazo a 16–18px (lucide default actual). En Ionicons usar variantes **outline** para igualar ese peso visual. |
| **Alineación** | Centrado óptico con el texto; icono no dicta el line-height; en línea con texto, `vertical-align: middle` + nudge fino. Icono y label comparten baseline visual. |
| **Color** | **`currentColor` por defecto** (hereda el token de texto). Iconos de estado usan el token de estado; decorativos usan `text-tertiary`. **Nunca negro puro.** |
| **Estados** | default `text-secondary` · hover `text-primary` · activo/seleccionado `accent`/`brand` · deshabilitado `text-tertiary` (opacidad reducida) · destructivo `danger`. |
| **Decorativos** | `aria-hidden="true"`, sin foco, sin `title`. Acompañan texto que ya comunica. |
| **Interactivos** | Botón solo-icono: **`aria-label` obligatorio**, target táctil **≥44px** (aunque el glifo sea 18), foco visible. |
| **Relleno vs outline** | **Outline primero** (coherente con lucide). Filled solo para **estado activo/seleccionado** (p.ej. tab activo). No mezclar arbitrariamente. |

### 7.3 Mapa semántico compartido (el verdadero contrato)

Para que dos librerías "signifiquen lo mismo", el contrato es un **mapa concepto → (icono lucide, icono Ionicons)** que se completa en P1.4.4/P1.4.6. Ejemplos ya presentes que deben mantenerse consistentes: sincronización, alerta, animal, mapa/potrero, sanidad, reproducción, captura (+). Regla: **un concepto = un icono visualmente equivalente en ambas plataformas**. Si lucide y Ionicons no tienen equivalente cercano para un concepto, ese concepto es candidato a ícono custom (decisión futura, no ahora).

**⚠️ DECISIÓN E:** contrato = mapa semántico + reglas de forma; **dos librerías permitidas**, sin elegir vendor único (YAGNI). Ver §14.

## 9. Motion

**No se implementa. Se especifica.**

### 9.1 Duraciones (tokens)

| Token | ms | Uso |
|---|---|---|
| `motion-instant` | 75 | Hover/estado de nav (ya en uso: `duration-75`), feedback inmediato |
| `motion-fast` | 120 | Cambios de estado de control, checkbox, toggle |
| `motion-base` | 200 | Aparición de overlays, toasts, expand/collapse |
| `motion-expressive` | 300 | Drawers, modales, transiciones de página |
| `motion-slow` | 500 | Solo casos especiales (skeleton shimmer, énfasis) |

### 9.2 Curvas

| Token | Curva | Uso |
|---|---|---|
| `ease-out` | `cubic-bezier(0.16, 1, 0.3, 1)` | **Entradas** (aparecer, expandir) — arranca rápido |
| `ease-in` | `cubic-bezier(0.4, 0, 1, 1)` | **Salidas** (desaparecer) |
| `ease-in-out` | `cubic-bezier(0.4, 0, 0.2, 1)` | **Movimientos** (reposicionar, reordenar) |
| `spring` (móvil) | resorte suave | Press del FAB (ya: `scale 0.95`), gestos táctiles |

### 9.3 Cuándo animar

- Feedback de acción (guardado ✓, error), entrada/salida de overlays, cambios de estado de control, indicador de sync (ya: `animate-ping` del dot), press táctil.

### 9.4 Cuándo NO animar

- **Re-render de tablas/listas densas** (distrae y cuesta performance con cientos de filas).
- **Captura en manga** (acción repetida cientos de veces: cero fricción, sin animaciones entre registros).
- Cambios de dato de KPI en vivo (el número cambia, no "vuela").
- **`prefers-reduced-motion`: obligatorio.** Se desactiva toda animación no esencial; las esenciales (feedback) se reducen a fade mínimo o cambio instantáneo. Regla de a11y (§10).

| **Movimiento** | Respetar `prefers-reduced-motion` (§9.4). |
| **Idioma/i18n** | `lang` correcto; el ERP es internacional (AR/UY/MX/CO/US/BR) → textos no truncados por layout, números/fechas localizados (presentación por TZ del establecimiento es deuda conocida). |

## 11. Responsive

**No se implementa. Se define.** El reparto de responsabilidad es claro (ADR-0012): **la app nativa es dueña del móvil real; la web es escritorio/tablet primero.** Pero la web debe degradar con dignidad, no romperse.

### 11.1 Breakpoints

| Token | Rango | Contexto |
|---|---|---|
| `xs` | < 480 | Móvil web (fallback; el móvil real es la app) |
| `sm` | 480–767 | Móvil grande / phablet |
| `md` | 768–1023 | **Tablet** (primer target táctil web serio) |
| `lg` | 1024–1439 | **Desktop** — aparece la sidebar |
| `xl` | ≥ 1440 | Wide — más columnas, más densidad |

Alinea con el `lg` que ya es el corte de la sidebar (`max-lg:hidden`).

### 11.2 Comportamiento

- **Navegación (gap crítico).** Hoy, bajo `lg`, la sidebar desaparece **sin reemplazo** → la web queda **sin navegación** en tablet/móvil. Contrato: bajo `lg`, la sidebar colapsa a **top bar + drawer** (hamburguesa) usando el mismo `SECTIONS`. Ver §14.
- **Layouts.** Grilla de KPIs: 4 col (`xl`) → 2 (`md`) → 1 (`xs`). Formularios: multi-columna en `lg+`, **una columna** en `md-`. Padding de página: 24 (`lg+`) → 16 (`md-`).
- **Tablas densas** (el caso duro): en `lg+` tabla completa; en `md-` → **scroll horizontal** dentro de contenedor `overflow-x-auto` **o** colapso a tarjetas por fila (según tabla; el `DataTable` P1.4.4 define la estrategia por columna prioritaria). Nunca romper el layout de página.
- **Overlays:** modal centrado en `lg+`; **sheet inferior** (drawer) en `md-`.

### 11.3 Reparto web/móvil

- La **web** cubre desktop y tablet con calidad; el móvil web es fallback digno (no pixel-perfect).
- La **app** cubre el campo. No se duplica la experiencia (ADR-0012): el móvil-web no intenta ser la app.

| **B** | **Grid base de spacing** (4px + sub-unidad 2px documentada vs 4px puro) y la **escala de spacing** como token. | **4px base + 2px sub-unidad acotada a detalle óptico.** Coincide con el uso real; no rompe medios pasos existentes. |
| **C** | **Densidad como capa multiplicadora en runtime** (`data-density` + CSS vars / objeto de tema móvil), introducida como tokens **desde P1.4.3**. Qué cambia (spacing/alturas) y qué nunca (tipo, color, semántica, a11y). | **Introducir la capa desde P1.4.3 con un solo modo.** Es la decisión de mayor costo si se difiere (DR6). |
| **D** | **Dark mode:** web = `data-theme` **controlado por usuario** (migrando del `@media` accidental), dark como target **auditado** en P1.4.7; móvil = **claro primero, dark diferido** (tokens dark conservados, no cableados). Cambia la generación del CSS (media-query default + override por atributo + anti-FOUC). | Adoptar la recomendación de §6.3. |
| **E** | **Iconografía:** contrato = **mapa semántico compartido** + reglas de forma/tamaño/estado; **dos librerías permitidas** (lucide web + Ionicons móvil), sin vendor único (YAGNI). | Adoptar §7. Elegir vendor único queda explícitamente **fuera** (revisable si aparece un target que lo exija). |
| **F** | **Estándar de accesibilidad = WCAG 2.1 AA** como piso de aceptación (contraste, foco, teclado, 44px touch, SR, estado no-solo-color, reduced-motion). | Adoptar §10 como contrato permanente. |
| **G** | **Breakpoints + resolución del gap de navegación web < lg** (sidebar → top bar + drawer). Reparto web(desktop/tablet)/app(campo). | Adoptar §11. |

### 14.2 NO debe registrarse en ADR-0014 (es spec/token, no arquitectura)

- Los **valores exactos** de cada rol tipográfico, cada peldaño de spacing, cada duración de motion. Viven en la spec y en `tokens.ts`; cambian sin ADR (con `tokens:build`).
- La **API concreta** de cada componente (props, nombres). Es diseño de implementación de P1.4.4+.
- **Qué icono exacto** representa cada concepto (el mapa §7.3 es tabla viva, no decisión de arquitectura).
- **Valores de curvas/duración** de motion (spec-level).
- El **orden interno** de construcción de primitivos dentro de cada familia.
